# Evaluate Run

issue-loop の1回の実行を、(1) セッションログから事実を復元し、(2) 期待ワークフロー（このリポジトリの `commands/issueloop.md`・`workflows/iteration.js`）と突合し、(3) 正常動作・バグ・設計課題に分類して報告する手順。

以下で「スクリプト」はこのスキルのベースディレクトリ配下の `scripts/` を指す。

## 引数（任意）

`$ARGUMENTS` で対象を指定できる。未指定なら対象プロジェクトを質問するか、文脈から特定する。

- 対象プロジェクトのパスまたは名前（例: `my-room`）
- セッション ID（分かっている場合）

## 調査の原則

- **仮説駆動で進める**: 各フェーズは「仮説 → 取得するデータ → 取得方法 → 判断基準」の順で考える。データを先に集めて眺めるのではなく、確認したい仮説を決めてから最小限のデータを取る。
- **ログの主張を鵜呑みにしない**: 「PRを作成した」「Issueを登録した」等のエージェントの発言は、必ず外部状態（`gh`、リポジトリ内ファイル）で裏取りする。
- **メインセッションはオーケストレーションのみ**: 実装・レビュー等の実作業は別ファイルのサブエージェント transcript にある。メインだけ読んで評価を下さない。
- 読み取り専用で調査する。対象プロジェクトの状態ファイルや Issue/PR を変更しない。

## 前提知識: ログの配置

- transcript: `~/.claude/projects/<ENCODED>/<sessionId>.jsonl`（1行1 JSON レコード）。`<ENCODED>` はプロジェクト絶対パスの `/` と `.` を `-` に置換したもの。
- **サブエージェント transcript**: `~/.claude/projects/<ENCODED>/<sessionId>/subagents/agent-<taskId>.jsonl`。バックグラウンド起動された Agent はここに保存される。メインセッション内の `<task-notification>` レコードの task-id と対応する。
- `sessions-index.json` は**古くなっていることがある**。セッション列挙はファイル自体の mtime を信頼する。
- セッション種別: 対話セッションは最初の user レコードに `<command-message>` やユーザー文が入る。SDK 起動セッションは先頭が `queue-operation`/`enqueue` で `promptSource: "sdk"`。
- push / PR 作成のタイミングで、ハーネスが自動起動するセキュリティレビューが**独立した SDK セッション**として同ディレクトリに残る。issue-loop 側の不具合と混同しないこと。

## フェーズ1: アンカーセッションの特定

- 仮説: 対象の実行は、対象プロジェクトの transcript ディレクトリ内で該当日時に更新されたファイル群にある。
- 方法: 引数からプロジェクトを解決し（名前だけなら `ls -d ~/.claude/projects/*<名前>*`）、`.jsonl` を mtime 降順で列挙。各候補の先頭数十行から種別と最初のプロンプトを確認する。
- 判断: `<command-name>/issue-loop:issueloop` を含む対話セッションがアンカー。その活動時間窓 `[開始, 終了]` を控える。同時間帯の他セッション（SDK 起動・別対話）は役割を推定してからフェーズ5以降で使う。

## フェーズ2: メインセッションのタイムライン復元

- 仮説: メインセッションには「セットアップ → Workflow 起動 → 戻り値（`signal`）確認 → 質問/完了処理」のオーケストレーションだけが現れるはず。
- 方法:

```bash
python3 <skill-base>/scripts/dump-timeline.py <アンカー.jsonl>
```

- 着目点:
  - Workflow ツールの戻り値の `signal`（`DONE` / `NO_ISSUE` / `NEEDS_INPUT` / `FAILED`）と、その後の分岐が手順どおりか
  - `args` を JSON オブジェクトとして渡しているか（JSON 文字列で渡すと workflow が即 `FAILED` を返す）
  - `RES ERR` 行（ツールエラー、ユーザーによる拒否・中断）
  - AskUserQuestion → `args.answers` 付きの `resumeFromRunId` 再起動の一連（イテレーション数を増やしていないか）

## フェーズ3: サブエージェントの一括要約

- 仮説: 実作業は workflow が起動したエージェント群にあり、起動時刻順に並べれば「PR同期 → Issue選定 → 情報収集 → 分類 → ブランチ作成 → 実装 → レビュー準備 → レビュワー並列 →（再ラウンド）→ 軽微修正 → スコープ外Issue登録 → PR作成 → PR検証」の系列が読み取れるはず。
- 方法: workflow の transcript ディレクトリにある `journal.jsonl`（各 `agent()` の実際の戻り値を記録）と `agent-<id>.jsonl`（各エージェントの transcript）を読む。`/close-issues` や `result-dashboard` など Agent ツール起動分は従来どおり:

```bash
python3 <skill-base>/scripts/summarize-subagents.py \
  ~/.claude/projects/<ENCODED>/<sessionId>/subagents/
```

- 判断: 各エージェントの IN（プロンプト）から役割を同定し、OUT / 構造化リターンが役割の完了を主張しているか確認する。`errors=` 付きのものと、OUT が途切れている・完了を主張していないものを深掘り対象にする。

## フェーズ4: レビューループの深掘り

- 仮説: レビューループの制御はスクリプトが決定的に行うため、逸脱があるとすればエージェント個々の作業内容（指摘の質・修正の実態・StructuredOutput の返答）にあるはず。
- 方法: `journal.jsonl` で各ラウンドの実行系列と戻り値を確認し、疑わしいエージェントの transcript に `dump-timeline.py` を適用する。
- 着目点:
  - レビューラウンド数と各ラウンドの blocking 指摘、maxReviewIterations の遵守
  - fail のまま上限到達した場合に PR へ警告コメントを投稿したか
  - CI 実行の有無（ci.sh が存在する場合）
  - schema 付きステップが StructuredOutput ツールを呼ばず本文に JSON を書いていないか

## フェーズ5: 外部状態との突合

- 仮説: ログが主張する成果（PR・Issue・状態ファイル）が実在し、内容が一致するはず。
- 方法（対象プロジェクトのディレクトリで実行）:
  - `ls .issue-loop/` と主要ファイルの中身 — 実行後の残存状態が妥当か（中断後に `NEEDS_INPUT` 等が残っていないか）
  - `gh pr view <番号> --json state,title,comments` — PR の実在と警告コメント
  - `gh issue list --json number,title,createdAt` — 実行時間帯に作成された Issue の数と質（スコープ外登録の暴発がないか）

## フェーズ6: 評価とレポート

期待ワークフローとの差分を次の4分類で整理する: **正常動作 / バグ（要修正） / 設計課題 / 効率・コスト**。

効率・コストは定量で評価する:

```bash
python3 <skill-base>/scripts/tokens-by-agent.py <アンカー.jsonl>
```

エージェント個別（起動時刻順）と役割×モデル別のトークン集計が出る。特定の役割・ラウンドへの偏り（例: レビューループが総消費の過半を占める）や、機械的な工程が上位モデルで動いていないかを確認する。

既知の失敗パターン（過去の評価で実際に観測されたもの）:

- レビューが収束しない（毎回新しい軽微な指摘が出て必ず上限到達する）
- スコープ外 Issue 登録の暴発（小さな変更から多数の Issue が生まれ、次のループの入力になり自己増殖する）
- schema 付きステップが StructuredOutput ツールを呼ばず、本文に JSON を書いて終了する（haiku で観測）
- `args` を JSON 文字列で渡してしまい workflow が即 `FAILED` を返す
- `args.pluginRoot` に誤ったパスが渡り、全エージェントが指示ファイルを読めない（メインセッションがプレースホルダを誤推測。フォールバックモデル実行で観測）
- 「外部ファイルを読んで指示に従え」型のサブエージェント起動が安全分類器にブロックされ、スクリプトには null（原因不明の失敗）としてしか見えない
- `FAILED` 後にメインセッションが規定の終了処理をせず、独自リカバリ（プラグイン修正・実装なしの PR 作成など）に走る（フォールバックモデル実行で観測）
- セッション全体がフォールバックモデルで動作している（`tokens-by-agent.py` の model 列で判明。逸脱の多くがモデル能力起因になる）

レポートは以下を含める:

1. 結論（完走したか、最重要の問題は何か）を冒頭1段落で
2. 実行タイムライン表（時刻 / 出来事 / 結末 ✅⚠️❌）
3. 正常動作した点・問題点（上記4分類、それぞれ根拠となるログの位置を添える）
4. 主要ログのフルパス一覧（ユーザーがそのまま開けるように）
