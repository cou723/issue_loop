# Issue 統合

オープン Issue の中から同種の細かい Issue をまとめ、Issue リストの見通しを保つ。統合は「統合 Issue を新規作成し、元 Issue をクローズする」という復元しづらい操作のため、必ずユーザーの承認を得てから実行する。

## ステップ 1: データ取得

以下を並列で実行する:

- `gh issue list --state open --limit 100 --json number,title,body`
- `gh pr list --state open --json number,title,body,headRefName`

オープン Issue が2件未満なら「統合すべき Issue がありません。」と表示して終了する。

## ステップ 2: 統合対象外 Issue の特定

オープン PR が参照している Issue は統合対象から除外する。クローズするとマージ時の自動クローズ（`Closes #N`）やトレーサビリティが壊れるため。

以下のいずれかに該当する Issue を除外する:

1. オープン PR の本文またはタイトルに `#<Issue番号>` への言及がある
2. オープン PR のブランチ名（`headRefName`）に Issue 番号が含まれる（例: `issue-42-...`, `fix/42-...`）

## ステップ 3: 統合案の作成

エージェントは使わず、このコマンド自身がステップ1のデータから統合グループ（2件以上の Issue の組）を作る。判断基準は issue-update エージェントの統合基準に揃える:

- 根本原因や対処方針が同一とみなせる Issue は同じグループにする
- 対象コンポーネントやファイルだけが異なり問題の種類が同じ場合は統合する。ビジネスロジックや対象が全く異なる問題は統合しない
- 迷う場合は統合しない（保守的に判断する）
- 統合後のタイトルは個別コンポーネント名を除いた横断的な表現にする

グループが0件なら「統合すべき Issue はありませんでした。」と表示して終了する。

## ステップ 4: ユーザー承認

まず統合案を一覧表示する:

```
以下の統合案があります:

  A. 「<統合後タイトル>」 ← #12, #15, #23
  B. 「<統合後タイトル>」 ← #18, #31
```

その後 `AskUserQuestion`（multiSelect: true）で実行するグループを選択させる。各グループを1つの選択肢とし、label に統合後タイトルの要約、description に統合元の Issue 番号一覧を入れる。1質問の選択肢は最大4つのため、グループが5つ以上ある場合は複数の質問に分割する（最大4質問。16グループを超えた分は今回の対象から外し、その旨を表示する）。

## ステップ 5: 統合の実行

承認されたグループごとに以下を行う:

1. `gh issue create --title "<統合後タイトル>" --body "<本文>"` で統合 Issue を作成する
   - 冒頭に「[issue-loop] 以下の Issue を統合したものです」と経緯を記載する
   - 統合元の各 Issue を `- #<番号> <タイトル>: <本文の要点>` 形式で箇条書きし、統合によって情報が失われないようにする
2. 統合元の各 Issue をクローズする:
   - `gh issue close <番号> --comment "[issue-loop] Issue #<統合Issue番号> に統合しました。"`

## ステップ 6: 結果表示

「✅ <グループ数> 件の統合を実行しました（<統合元 Issue 数> 件 → <グループ数> 件）。」と表示する。承認されなかったグループがあれば「スキップ: <件数> 件」を併記する。
